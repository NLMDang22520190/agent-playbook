# 03 - Pilot plan: built-in review vs the playbook reviewer's checks 4-6

## Question
Can reviewer checks 4 (correctness), 5 (scope and slop) and 6 (security) be replaced by the harness review
(`/code-review` and `/security-review` in Claude Code, `/review` in Codex) without finding fewer real defects or costing more review time?
Checks 1, 2, 3, 7 stay in any case (no built-in found that does them, spec F9).

## Design: paired, same diff
Both arms review the **same finished diff**, so task difficulty cancels out. Review is read-only, so the arms do not disturb each other.
- **Arm A (built-in only):** run the built-in review on the diff. Nothing else.
- **Arm B (built-in + playbook checks 4-6):** run the playbook reviewer with checks 4-6 as in `roles/reviewer.md` today, plus the built-in review's findings.
- Each arm runs in a fresh context, with the same model and effort per harness. Record both in the log.
- Findings are merged and de-duplicated by a human (the user) who labels each: real defect / style / false alarm / unsure.
  The labeller does not see which arm found it.
- A is a subset of B by construction, so the question is whether B's extra findings are real and worth their cost.

## Two sets of tasks
1. **Seeded set (recall), 6 small tasks.** Take an existing small repo or the company's, and for each task plant one known defect in a
   finished change: off-by-one, missing authz check, swallowed error, scope creep (unrelated file edited), dead code, injection through a string-built query.
   Recall = planted defect found / planted. Seeds are written by someone who does not run the arms.
2. **Real set (precision and cost), 10 real tasks** from the onboarding period (month 1 is learning-only, so use small tasks from month 2, or
   past merged PRs replayed from their base sha). Collect: findings labelled real vs false alarm, minutes of review, defects found after merge.

## What to record per task (one row, append to `pilot-log.tsv` in the scratch folder, not the repo)
`task, set, harness, model, effort, arm, seconds, tokens, findings_total, findings_real, findings_false, planted_found, postmerge_bugs, note`
Use `cost.sh add --task <id> --role reviewer --weight <W> --seconds .. --tokens .. --majors <real majors>` for arm B so `cost.sh calibrate` can summarise;
tokens `0` when the harness does not report them, never a guess. Post-merge bugs have no field in `cost.sh` [VERIFIED from its header]; keep them in the log.

## Decision rule (write it before running)
Remove checks 4-6 from the role only if all hold:
- Seeded set: A finds at least as many planted defects as B, or the gap is one defect or less out of six.
- Real set: B's real findings that A missed are at most 2 of the 10 tasks, none of them a blocker.
- B costs more review time than A (otherwise the extra checks are free and stay).
Otherwise keep the checks, and shorten only the wording.
With 16 tasks this shows direction, not statistical proof. Report counts, not percentages, and say so.

## Threats to the result
- One labeller, who knows the planted defects: label the real set only after the seeded set is done and the seeds are forgotten, or ask a colleague.
- Model drift: the built-in review's model and prompt can change between runs; log the harness version.
- The seeded defects are chosen by a person and may favour one arm. Use a mix; include at least two the playbook checklist names and two it does not.
- Codex `/review` focuses on "behavior changes and missing tests" per its docs; it may behave differently from Claude's, so report per harness, do not pool.
- Company code and diffs go only to the model providers already approved for company work. Do not run the pilot on company repos with a personal account unless that is permitted: ask first.

## Steps
1. Pick the repo(s) and the labeller; confirm the company allows the harnesses on that code. (User)
2. Write the six seeded changes and the decision rule into the log header. (Someone other than the runner)
3. Run both arms on each seeded task in Claude Code; repeat in Codex for the same tasks if Codex is installed with the skills (spec W1). (Agent)
4. Label seeded findings, compute recall per arm and harness.
5. From month 2, run both arms on each real task after the work is finished, before the PR; label; record post-merge defects 4 weeks later.
6. Apply the decision rule; update the spec (W6-1) and the reviewer role accordingly.

Time: step 3-4 about half a day; step 5 spread over the first 10 real tasks; post-merge window 4 weeks. [INFERRED estimate]
