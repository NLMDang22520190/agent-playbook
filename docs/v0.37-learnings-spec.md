## Goal
Keep `.agents/LEARNINGS.md` small, current and trusted as it grows: tell the user when the file no longer
fits what the hook injects, flag entries that may be stale, keep unapproved lesson proposals instead of
losing them, and let the model *propose* clean-ups that the user approves. The model never edits the
file on its own.

**Weight:** per slice. S1, S2, S6: Lite (read-only or docs, reversible). S3, S4, S5: Full (S3 changes the file
format and an output shape, S4 adds a new agent-written file and changes the procedure in `playbook-learn`,
S5 adds a model-driven procedure over text that agents wrote). Escalate any Lite slice to Full if it grows.

## Understanding
- **The request, restated:** make the learnings mechanism maintainable over months, using the ideas that
  fit the playbook (inputs stay unmodified, humans review outputs, evidence and source rules stay) and
  rejecting the ones that do not (automatic writes by the model, transcript mining).
- **Other readings:** (a) adopt an automatic "dream" that rewrites memory: rejected, it breaks the rule that
  only user-approved, evidenced lessons are stored. (b) install a community dream skill: rejected, it works on
  Claude Code auto memory and has no evidence or approval model; two candidates were seen with audit
  warnings [UNVERIFIED, third-party listing]. (c) leave as is: possible, see "Cost of doing nothing".
- **In scope:** `learn.sh`, `learnings-hook.sh` (read-only use), `playbook-learn` skill text, setup text.
- **Out of scope:** the always-on block, the other skills, any Managed Agents or cloud dependency, a global
  cross-project store, mining of session transcripts, a model-applied merge.

## Eval scenarios to add (names only; assign E-numbers when merging)
- new: `check` warns when active entries exceed the hook budget and exits 0 when nothing else is wrong.
- new: `stale` flags an old entry and an entry whose scope matches no tracked file, and nothing else.
- new: review proposal on a fixture with a near-duplicate pair; file hash unchanged; no invented claim.
- new: review proposal on a fixture with an injected instruction in an entry; flagged, not obeyed.
- new: candidate captured in a non-interactive run is written to the queue, not to `LEARNINGS.md`.
- new: `promote` refused for a duplicate, a secret-looking rule, and a full file.

## Cost of doing nothing
The file keeps growing past what the hook injects and past the line budget, with retired entries eating
lines, and unapproved proposals continue to vanish at the end of a task. None of this fails loudly today
(F2, F3, F6). The benchmark evidence on stale memory (F8) is [UNVERIFIED]; the budget facts (F1 to F3) are not.

## Risks
- **Injection:** candidates and entries are agent-written text. They are never injected unreviewed (S4-3) and are
  treated as data in review (S5-5).
- **False positives in `stale`:** an old but correct rule gets listed. It only lists; `verify` resets the clock.
- **Complexity creep:** six slices for one file. If only one is built, build S1.
- **Windows path handling:** `git ls-files` pathspec behaviour differs from shell globs; test with a `**` scope.
